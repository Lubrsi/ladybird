# Direct Wasm-to-Cranelift frontend

Status: design and migration plan, 2026-08-06.

## Decision

Ladybird's persistent native compiler should lower the retained parsed and validated Wasm
`Expression` directly to typed Cranelift IR. It should not consume the storage locations and
synthetic instructions produced for the bytecode interpreter.

The existing allocated-bytecode frontend remains useful only during migration:

- as the per-function fallback when the direct frontend does not yet support an instruction;
- as a correctness fallback while the new frontend is validated; and
- as the natural compiler for a temporary OSR-enabled version that resumes an activation already
  running in the bytecode interpreter.

Normal calls and native-code cache entries should eventually use a clean entry-only body produced
by the direct frontend. A temporary OSR version may retain the existing interpreter-location state
model and synthetic checkpoint machinery because that version exists specifically to consume an
interpreter activation. It is migration scaffolding, not a second native backend to maintain. If
the direct frontend succeeds, replace this temporary OSR path and delete the allocated-bytecode
compiler wholesale; version control remains its archive.

## Why the frontend boundary is changing

The bytecode generator first reasons about individual values, then allocates them to R0-R7,
`ValueStack`, or call-record storage. That allocation is an interpreter optimization: it reduces
dispatches, stack-pointer changes, and repeated `ValueStack` traffic. The persistent bytecode keeps
the selected locations rather than the original per-definition value identities.

The current Cranelift frontend therefore receives an interpreter-allocated program and reconstructs
typed SSA from reused storage locations:

```text
typed Wasm values
    -> interpreter register and stack allocation
    -> reused R0-R7 / ValueStack locations
    -> Cranelift type banks and SSA reconstruction
    -> native register allocation
```

This creates native-only machinery for:

- separate `i32`, `i64`, `f32`, and `f64` banks for one interpreter location;
- bank normalization at control-flow edges;
- liveness reconstruction for R0-R7;
- virtual-stack location state across blocks and loops;
- aliases between ordinary Wasm operations and interpreter superinstructions; and
- pressure policies over state whose live ranges were shaped by interpreter allocation.

The replacement keeps interpreter and native allocation as separate consumers of the same Wasm
semantics:

```text
parsed, validated Wasm
    ├── interpreter lowering -> synthetic bytecode + R0-R7 / ValueStack allocation
    └── native lowering      -> typed Cranelift SSA
```

This conclusion follows measured attempts to improve the existing representation rather than a
preference for a different frontend shape:

- Removing canonical local and stack traffic produced large improvements but did not close the
  generated-code gap.
- Typed banks recovered useful type information but added explicit reconstruction machinery.
- Updating Cranelift and disabling synthetic tier-up did not close the gap.
- Exact R0-R7 edge liveness reduced native instructions by 4.7% in `unzReadCurrentFile()` and 2.5%
  in `AddActiveInteraction()`, proving false location liveness is costly but bounding the benefit
  available from eight registers.
- All-loop and selective OSR preheaders duplicated carried SSA state and grew native code.
- Peak-live, loop-live, and pressure-split policies were neutral or too small to justify their
  complexity.
- Wasmtime produces materially better code with the same Cranelift version when its frontend
  supplies typed Wasm value flow directly.

The problem is not that the interpreter has virtual registers or synthetic instructions. Those are
appropriate interpreter optimizations. The problem is treating their output as the native
compiler's semantic value model.

## Retained source representation

`Expression` retains the parsed instruction stream in `Types.h`. The same object also owns
`compiled_instructions`, which contains the separately generated bytecode dispatch stream. The
validator has accepted the retained instruction stream before native compilation is requested.

The original raw Wasm binary does not need to be retained or decoded again. The direct frontend
does need to reconstruct operand identities and typed control state: the validator currently does
not persist its operand stack or a per-instruction SSA graph.

The parser appends `synthetic_end_expression` as an internal sentinel. The direct input may
temporarily recognize that sentinel or replace it with explicit function-boundary metadata. It
should not otherwise consume synthetic bytecode instructions.

## Scope

### Replaced state-model machinery

The direct frontend should not use:

- `CraneliftInsn.sources` or `CraneliftInsn.destination`;
- R0-R7 as persistent Cranelift `Variable` identities;
- register or virtual-stack `Bank` tracking;
- register-bank or stack-bank normalization;
- bytecode register liveness;
- interpreter call-record allocation as the native calling convention;
- `synthetic_br_nostack`, fixed-arity synthetic call variants, local-index superinstructions, or
  fused local/constant operations; or
- `synthetic_tier_up` as an instruction in the clean native body.

### Shared infrastructure

The following work is independent of the frontend state model and remains applicable:

- the existing native-to-native call and relocation machinery, subject to the cross-flavor ABI
  decision below;
- indirect-call target lookup, type checks, and traps;
- Cranelift user trap codes and compiled fault recovery;
- memory alias regions and immutable runtime metadata;
- runtime layout offsets and helper imports;
- relocation collection and patching;
- code installation, native entry publication, and cache blobs;
- incremental compilation planning and publication; and
- benchmark, CLIF, native-instruction, and Instruments analysis tools.

Individual emitters may still need an interface change. For example, native indirect-call target
resolution is common, while loading its arguments from interpreter call-record storage belongs only
to the old frontend.

## Initial Rust module boundary

Do not begin with a broad mechanical split of `compiler.rs`. First build the differential harness
described below. The next checkpoint should then extract only code that is independent of bytecode
operand locations.

Use the existing `compiler.rs` module as the public driver while adding submodules:

```text
compiler.rs                     existing driver and allocated-bytecode frontend
compiler/common.rs              runtime, ABI, trap, and final-code environment
compiler/direct.rs              typed Expression-to-CLIF frontend
compiler/register_liveness.rs   allocated-bytecode analysis
```

The first `common.rs` extraction should include:

- `WasmMemoryFlags` and alias-region creation;
- Wasm type to Cranelift type conversion;
- payload conversion used only at interpreter/native boundaries;
- user trap-code conversion;
- runtime layout and imported-helper descriptions; and
- relocation serialization and final machine-code extraction.

Do not move the current `native_signature` behind a generically named permanent interface yet. Its
signature always carries interpreter and configuration pointers plus a resume token, and functions
above eight parameters receive a call-record pointer instead of typed parameters. Extracting it may
be useful as `LegacyNativeAbi`, but the direct frontend's body ABI is an explicit design decision.

A useful shape is a function environment containing runtime facts but no operand state:

```rust
struct FunctionEnvironment {
    pointer_type: Type,
    memory_flags: WasmMemoryFlags,
    runtime_layout: RuntimeLayout,
    helpers: ImportedHelpers,
}
```

Emission methods should take `&mut FunctionBuilder`; the environment should not own the builder.
It must not contain R0-R7 banks, virtual-stack state, bytecode source/destination addresses, or
legacy control frames.

Do not initially move `decode_indirect_call_type`, `emit_indirect_call_with_record`, register/stack
read and write macros, `Bank`, or the existing `ControlFrame`. Their current interfaces expose the
old state model. Extract a common typed operation only after both frontends need it.

For example, indirect calls should eventually have this shape:

```text
common typed target lookup, type check, and native call
                 ^                         ^
      direct typed SSA arguments   legacy call-record adapter
```

The behavior-preserving extraction must leave emitted native code byte-for-byte unchanged for the
existing diagnostic functions before the direct frontend is added.

## Direct frontend state

The direct frontend constructs semantic state from validated Wasm instructions.

### Operand stack

Maintain a typed operand stack whose entries are Cranelift `Value`s. Ordinary operations pop their
typed inputs and push their typed results. The frontend must represent unreachable polymorphic
stack state explicitly rather than forcing live values into interpreter storage.

### Structured control stack

Maintain a separate direct-frontend control frame for each function, block, loop, if, and supported
exception construct. A frame records at least:

- construct kind;
- entry operand-stack height;
- parameter and result types;
- branch destination and continuation blocks;
- reachability; and
- the typed values or block parameters required by the appropriate branch edge.

Branches use Wasm label depth to select a frame, truncate the operand stack to the frame's entry
height, and pass the construct's declared values as explicit Cranelift block arguments. Genuine
Wasm merge values remain block parameters; unrelated interpreter locations do not.

Control-flow construction is expected to be the bulk of the new frontend. Per-operation Cranelift
emission is largely reusable once it accepts typed operands rather than bytecode locations.

### Locals

Wasm locals remain mutable source-language storage. The initial direct frontend may represent them
with typed Cranelift `Variable`s. This is distinct from representing interpreter scratch registers
as mutable variables. Measure the resulting local block parameters before adding any new local-home
or liveness policy.

### SIMD and references

The direct frontend's type model should include every supported Wasm value kind, including `V128`,
from the start. Individual instruction families may fall back while coverage is incomplete. Do not
add a `V128` bank to the allocated-bytecode frontend as part of this migration.

## Direct compiler input

Do not reuse the current post-allocation `CraneliftInsn` format as the direct frontend's input. Its
sources, destination, synthetic operations, call-record choices, and continuation records encode
the representation being retired.

Define a distinct serialized direct-instruction representation containing semantic instruction
data only. It needs to preserve the information already present in the retained `Instruction`
objects, including:

- opcode and immediates;
- local, global, memory, table, function, type, tag, data, and element indices as applicable;
- block type, end, and else structure;
- branch label depths and complete `br_table` target vectors; and
- memory argument alignment, offset, and memory index.

Variable-length data such as `br_table` targets should use an explicit side region rather than
synthetic continuation instructions. The compile-subprocess input must also provide the module
types and runtime facts required by the supported instructions. Existing function and local type
tables can be reused where their semantics match.

The input batch and native cache format need an explicit frontend or code-flavor discriminator so
direct, allocated-bytecode, and future OSR variants cannot be confused.

## Eligibility and migration

Migration temporarily uses three per-function tiers:

1. direct typed frontend;
2. existing allocated-bytecode frontend; and
3. bytecode interpreter.

Unsupported direct instructions must reject the whole function cleanly and select the next tier;
they must not partially compile a body. Add instruction families generally rather than adding a
workload-specific subset.

Suggested implementation checkpoints:

1. Build the differential native/interpreter harness.
2. Extract `compiler/common.rs` with no generated-code change.
3. Define and version the direct instruction and module-context serialization.
4. Separate clean-entry and OSR-capable runtime publication before a direct body can publish.
5. Add `compiler/direct.rs` with typed operand and structured control stacks.
6. Compile clean entry-only scalar functions through the direct path, with per-function fallback.
7. Add structured control flow early enough to test the architectural premise rather than
   measuring only straight-line code.
8. Migrate memory, globals, tables, direct calls, indirect calls, conversions, references,
   exceptions, and SIMD as complete instruction families.
9. Re-profile `unzReadCurrentFile`, `AddActiveInteraction`, SHA-512, CoreMark's reported score, and
   the full Wasm benchmark set before considering new state or pressure policies.

Each checkpoint should be independently testable and committed. Do not port a legacy bank,
location-liveness, or synthetic-op optimization merely to preserve existing work.

### Retirement of the allocated-bytecode frontend

The three-tier arrangement is a staged rollout, not the intended final architecture. The
allocated-bytecode frontend receives correctness fixes and only the minimum interoperation work
needed to unblock migration. Do not add new optimization policy, opcode-family implementations, or
permanent abstractions to it. In particular, the direct frontend's typed state model and durable
native ABI must not conform to interpreter allocation locations merely to prolong mixed-flavor
operation.

Retire the old frontend in explicit stages:

1. Use it as the per-function native fallback while direct instruction-family coverage grows.
2. Stop using it for fresh entry once the direct frontend covers every function the old frontend
   could compile and the direct path has passed differential, specification, and workload tests.
3. Keep it only as a temporary OSR compiler while the direct OSR path or another production tier-up
   design is completed and validated.
4. Delete it once fresh entry, native calls, indirect calls, incremental publication, the native
   cache, and interpreter-to-native tier-up no longer depend on allocated-bytecode compilation.

Deletion includes its serialized compiler input, banks and location-state reconstruction,
synthetic-instruction lowering, legacy native ABI, cross-flavor relocation selection, adapters, and
OSR-only compiler path. Retain only infrastructure that is independently required by the direct
frontend or runtime, such as trap lowering, relocation representation, alias regions, publication,
and cache plumbing.

Benchmark and profile the retirement checkpoint against the old frontend, but do not retain the
old frontend as a runtime option solely for comparison. The interpreter remains the startup and
cold-function tier and the correctness oracle; removing the old native frontend does not remove the
bytecode interpreter.

## Differential verification harness

Build the verification harness before the direct frontend. A wrong reaching definition, block
argument, stack truncation, or conversion can silently miscompile rather than crash.

`LADYBIRD_CRANELIFT_COMPILER=/usr/bin/false` already provides an interpreter-only oracle. The
harness must run equivalent inputs with native compilation enabled and disabled, then compare:

- returned values, including exact integer and deterministic floating-point bit patterns;
- traps and trap reasons;
- mutable globals;
- linear-memory contents and size;
- table-visible effects;
- imported function calls and observable host effects; and
- behavior across repeated calls and fresh instances.

Existing expected-result tests remain valuable but are not themselves differential. The harness
should make it easy for every newly migrated instruction family to run in both modes. It must avoid
native cache reuse when a cold compilation is required and must distinguish harness wall time from
the program's measured compilation and execution phases.

### Floating-point and relaxed-result policy

The local WebAssembly specification states that some numeric operators are non-deterministic
because they may return one of multiple NaN values. NaN propagation requires a canonical payload
when all NaN inputs are canonical (including no NaN inputs); otherwise any arithmetic-NaN payload
is permitted outside the deterministic profile. `fneg`, `fabs`, and `fcopysign` are excluded from
that propagation rule and preserve or change specified sign/payload bits. Relaxed SIMD adds further
instruction-specific result sets.

The broad differential comparison must therefore not require identical NaN payloads whenever the
instruction semantics permit different payloads. At minimum, it should classify both results as
valid members of the permitted NaN class. Exact comparison remains required for bit-preserving
operations, reinterpretation, explicitly pinned payload tests, non-NaN values including signed
zero, and state whose bits are observed through integer reinterpretation or memory.

An end-to-end harness may not know which operation produced a returned or stored NaN. Its test
format therefore needs an explicit comparison policy: exact bits by default, with spec-derived NaN
or relaxed-result matching only for tests that opt into it. The core specification tests remain the
authority for canonical-versus-arithmetic NaN constraints; globally canonicalizing every NaN would
hide invalid results as well as suppress false differences.

## Cross-flavor calls

Mixed direct, allocated-bytecode, and interpreted functions must call one another correctly. That
is a hard migration invariant. It does not imply that the direct frontend must permanently adopt
the current native body ABI.

The current ABI is only partly representation-neutral:

- every body receives interpreter and configuration pointers plus an entry/resume token;
- functions with at most eight parameters receive typed arguments; and
- functions above that cutoff receive a pointer to call-record locals; and
- functions with more than one result are rejected from native compilation.

Sharing that ABI between both native frontends would make cross-flavor direct calls simple, and it
would not constrain the direct frontend's internal typed SSA. It would, however, preserve
interpreter-derived entry arguments and the high-arity call-record convention in direct-generated
call sequences. The existing ABI must therefore not become permanent merely because it is moved to
`common.rs`.

Before mixed direct-to-legacy relocations are enabled, choose and measure one of these boundaries:

1. Define a durable typed native body ABI and update the old frontend to consume it. The old
   frontend may need temporary marshalling from call-record storage for high-arity calls. Define
   multi-value returns in this ABI from the start rather than carrying forward the old frontend's
   one-result restriction; individual frontends may still fall back until their adapters support
   the complete result convention.
2. Give direct functions a clean body entry plus a legacy-compatible adapter, and provide the
   reverse boundary needed when direct code calls an old body. Adapters isolate legacy state but
   are deliberate migration code. Relocation patching then selects the symbol by caller flavor:
   old-frontend callers target the legacy adapter, while direct callers target the clean body.
   That selection belongs to the shared ABI/relocation layer, not either frontend.
3. During early bring-up, prohibit direct cross-flavor relocation patching and use the existing
   interpreter/helper boundary for mixed calls. This avoids ABI commitment but distorts call-heavy
   performance and cannot be the final mixed-module path.

The dependency direction remains important: neither frontend should privately define the eventual
body ABI. Once selected, a shared ABI module owns signatures, entry symbols, and relocation
contracts. Per-flavor ABI divergence is prohibited unless an explicit adapter owns the boundary.
ABI experiments then update the shared contract and cache version atomically rather than leaking
legacy locations into direct lowering.

## OSR and code flavors

The first direct frontend should produce clean entry-only code. It does not need to solve direct
OSR before demonstrating the generated-code benefit.

### Runtime publication capability

The current runtime publishes one interpreter-facing `cranelift_entry` pointer alongside the
`cranelift_native_entry` body pointer used by compiled callers. Fresh interpreter entry calls
`cranelift_entry` when non-null, and `synthetic_tier_up` polls that same pointer and enters it with a
nonzero checkpoint IP. That is safe only while every published adapter understands both entry
modes. A clean direct adapter has no resume dispatch and must never be entered by a polling
checkpoint.

Before any clean direct body can publish, runtime metadata must distinguish at least:

- an entry capable of starting a fresh activation; and
- an entry capable of resuming this bytecode activation at a checkpoint.

Separate acquire/release-published entry pointers are preferable to treating one pointer plus a
flavor bit as mutually exclusive, because a clean direct body and a temporary OSR body may coexist.
Fresh calls select the clean entry. A synthetic checkpoint polls only the OSR-capable entry; seeing
only a clean entry must keep interpreting and may register or trigger demand for the temporary OSR
flavor. Publication, request suppression, cancellation, and reclamation must remain safe when the
interpreter and compiler processes race.

The successful-transfer counter continues to count only an actual checkpoint-to-OSR handoff, not
clean publication or an OSR request. Its trace should identify the function, checkpoint, and code
flavor or generation. The one-way regression test must add the two-flavor seam:

1. publish a clean-only entry while an activation is interpreting;
2. prove a checkpoint does not enter it or increment the transfer counter;
3. publish an OSR-capable entry and prove exactly one transfer;
4. prove the following fresh call uses clean code without another OSR transfer; and
5. keep the OSR code alive until the transferred activation returns.

This publication split is independently testable with the old frontend before `compiler/direct.rs`
exists. Publish its interpreter-facing adapter as clean-entry-capable while withholding the
OSR-capable pointer, prove checkpoints continue interpreting, then publish the same capable adapter
for OSR and prove the handoff. The existing counter increment currently occurs immediately after a
non-null `cranelift_entry` poll; it must move to the successful OSR-capable path for this test to
retain its meaning.

When a function is compiling while an interpreter activation is already running:

1. Publish the clean direct body for future calls and store only that flavor in the normal cache.
2. If a live activation can benefit, request an allocated-bytecode OSR flavor using the existing
   checkpoint and interpreter-location machinery.
3. Allow that activation to transfer into the temporary flavor.
4. Retain the temporary code until every transferred activation has returned, then reclaim it.
5. Discard an unused result when no interested activation remains.

This policy preserves the demonstrated d3wasm tier-up staircase without permanently charging fresh
or cached calls for OSR dispatch and resume predecessors.

The expected replacement for the temporary allocated-bytecode OSR compiler is a direct OSR
variant. It would require a side table mapping the live typed Wasm state at each checkpoint to its
interpreter R0-R7, `ValueStack`, local, and runtime locations. The resume adapter would import only
those values into an OSR-specific direct variant. This is not a prerequisite for the first direct
frontend, but it is part of retiring the old compiler and must not add resume state to the
persistent clean body.

## Success criteria

Correctness is required before performance attribution:

- differential results agree across migrated instruction families;
- existing Rust, focused native-execution, broader LibWasm, and JS Wasm suites pass;
- unsupported functions fall back deterministically; and
- cache and relocation formats distinguish all code flavors.

The first performance comparison should use identical Cranelift versions and compiler settings.
Measure separately:

- optimized CLIF blocks, instructions, values, and block parameters;
- native code size, instruction count, loads, stores, and stack-memory operations;
- fixed native frame size;
- native compilation time and compiler memory;
- execution time or workload-reported score; and
- d3wasm loading and heavy-scene profiles.

Expected improvements are the removal of spurious joins, bank conversions, interpreter-location
live ranges, and synthetic-instruction decoding. Genuine Wasm merge parameters, mutable-local
state, runtime calls, traps, and register-allocation spills remain. Direct lowering should not be
judged by an expectation of zero block parameters or exact Wasmtime parity.

## Open decisions

- Exact direct-instruction serialization and variable-length side-table layout.
- Whether the direct frontend reconstructs all validation types or receives selected persisted
  validator metadata.
- The durable native body ABI and the temporary cross-flavor boundary used before it is available.
- The typed multi-value return convention and interpreter/legacy adapter marshalling.
- The smallest complete opcode-family milestone that usefully exercises structured control flow.
- Ownership and lifetime model for temporary OSR code.
- Whether native-only inlining begins as an `Expression` transform or is deferred until the direct
  frontend has a stable typed representation.
- The milestones at which the allocated-bytecode frontend becomes OSR-only and is then deleted.
