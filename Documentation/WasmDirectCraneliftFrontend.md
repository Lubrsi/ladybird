# Direct Wasm-to-Cranelift frontend

Status: design and migration record, updated 2026-08-26.

## Decision

Ladybird's persistent native compiler should lower the retained parsed and validated Wasm
`Expression` directly to typed Cranelift IR. It should not consume the storage locations and
synthetic instructions produced for the bytecode interpreter.

The existing allocated-bytecode frontend remains useful only during migration:

- as the per-function fallback when the direct frontend does not yet support an instruction;
- as a correctness fallback while the new frontend is validated; and
- as the natural compiler for a temporary OSR-enabled version that resumes an activation already
  running in the bytecode interpreter.

Normal calls and native-code cache entries should eventually use a clean entry-only body produced
by the direct frontend. A temporary OSR version may retain the existing interpreter-location state
model and synthetic checkpoint machinery because that version exists specifically to consume an
interpreter activation. It is migration scaffolding, not a second native backend to maintain. If
the direct frontend succeeds, replace this temporary OSR path and delete the allocated-bytecode
compiler wholesale; version control remains its archive.

## Why the frontend boundary is changing

The bytecode generator first reasons about individual values, then allocates them to R0-R7,
`ValueStack`, or call-record storage. That allocation is an interpreter optimization: it reduces
dispatches, stack-pointer changes, and repeated `ValueStack` traffic. The persistent bytecode keeps
the selected locations rather than the original per-definition value identities.

The current Cranelift frontend therefore receives an interpreter-allocated program and reconstructs
typed SSA from reused storage locations:

```text
typed Wasm values
    -> interpreter register and stack allocation
    -> reused R0-R7 / ValueStack locations
    -> Cranelift type banks and SSA reconstruction
    -> native register allocation
```

This creates native-only machinery for:

- separate `i32`, `i64`, `f32`, and `f64` banks for one interpreter location;
- bank normalization at control-flow edges;
- liveness reconstruction for R0-R7;
- virtual-stack location state across blocks and loops;
- aliases between ordinary Wasm operations and interpreter superinstructions; and
- pressure policies over state whose live ranges were shaped by interpreter allocation.

The replacement keeps interpreter and native allocation as separate consumers of the same Wasm
semantics:

```text
parsed, validated Wasm
    ├── interpreter lowering -> synthetic bytecode + R0-R7 / ValueStack allocation
    └── native lowering      -> typed Cranelift SSA
```

This conclusion follows measured attempts to improve the existing representation rather than a
preference for a different frontend shape:

- Removing canonical local and stack traffic produced large improvements but did not close the
  generated-code gap.
- Typed banks recovered useful type information but added explicit reconstruction machinery.
- Updating Cranelift and disabling synthetic tier-up did not close the gap.
- Exact R0-R7 edge liveness reduced native instructions by 4.7% in `unzReadCurrentFile()` and 2.5%
  in `AddActiveInteraction()`, proving false location liveness is costly but bounding the benefit
  available from eight registers.
- All-loop and selective OSR preheaders duplicated carried SSA state and grew native code.
- Peak-live, loop-live, and pressure-split policies were neutral or too small to justify their
  complexity.
- Wasmtime produces materially better code with the same Cranelift version when its frontend
  supplies typed Wasm value flow directly.

The problem is not that the interpreter has virtual registers or synthetic instructions. Those are
appropriate interpreter optimizations. The problem is treating their output as the native
compiler's semantic value model.

## Retained source representation

`Expression` retains the parsed instruction stream in `Types.h`. The same object also owns
`compiled_instructions`, which contains the separately generated bytecode dispatch stream. The
validator has accepted the retained instruction stream before native compilation is requested.

The original raw Wasm binary does not need to be retained or decoded again. The direct frontend
does need to reconstruct operand identities and typed control state: the validator currently does
not persist its operand stack or a per-instruction SSA graph.

The parser appends `synthetic_end_expression` as an internal sentinel. The direct input may
temporarily recognize that sentinel or replace it with explicit function-boundary metadata. It
should not otherwise consume synthetic bytecode instructions.

## Scope

### Replaced state-model machinery

The direct frontend should not use:

- `CraneliftInsn.sources` or `CraneliftInsn.destination`;
- R0-R7 as persistent Cranelift `Variable` identities;
- register or virtual-stack `Bank` tracking;
- register-bank or stack-bank normalization;
- bytecode register liveness;
- interpreter call-record allocation as the native calling convention;
- `synthetic_br_nostack`, fixed-arity synthetic call variants, local-index superinstructions, or
  fused local/constant operations; or
- `synthetic_tier_up` as an instruction in the clean native body.

### Shared infrastructure

The following work is independent of the frontend state model and remains applicable:

- the existing native-to-native call and relocation machinery, subject to the cross-flavor ABI
  decision below;
- indirect-call target lookup, type checks, and traps;
- Cranelift user trap codes and compiled fault recovery;
- memory alias regions and immutable runtime metadata;
- runtime layout offsets and helper imports;
- relocation collection and patching;
- code installation, native entry publication, and cache blobs;
- incremental compilation planning and publication; and
- benchmark, CLIF, native-instruction, and Instruments analysis tools.

Individual emitters may still need an interface change. For example, native indirect-call target
resolution is common, while loading its arguments from interpreter call-record storage belongs only
to the old frontend.

## Initial Rust module boundary

Do not begin with a broad mechanical split of `compiler.rs`. First build the differential harness
described below. The next checkpoint should then extract only code that is independent of bytecode
operand locations.

Use the existing `compiler.rs` module as the public driver while adding submodules:

```text
compiler.rs                     existing driver and allocated-bytecode frontend
compiler/common.rs              runtime, ABI, trap, and final-code environment
compiler/direct.rs              typed Expression-to-CLIF frontend
compiler/register_liveness.rs   allocated-bytecode analysis
```

The first `common.rs` extraction should include:

- `WasmMemoryFlags` and alias-region creation;
- Wasm type to Cranelift type conversion;
- payload conversion used only at interpreter/native boundaries;
- user trap-code conversion;
- runtime layout and imported-helper descriptions; and
- relocation serialization and final machine-code extraction.

Do not move the current `native_signature` behind a generically named permanent interface yet. Its
signature always carries interpreter and configuration pointers plus a resume token, and functions
above eight parameters receive a call-record pointer instead of typed parameters. Extracting it may
be useful as `LegacyNativeAbi`, but the direct frontend's body ABI is an explicit design decision.

A useful shape is a function environment containing runtime facts but no operand state:

```rust
struct FunctionEnvironment {
    pointer_type: Type,
    memory_flags: WasmMemoryFlags,
    runtime_layout: RuntimeLayout,
    helpers: ImportedHelpers,
}
```

Emission methods should take `&mut FunctionBuilder`; the environment should not own the builder.
It must not contain R0-R7 banks, virtual-stack state, bytecode source/destination addresses, or
legacy control frames.

Do not initially move `decode_indirect_call_type`, `emit_indirect_call_with_record`, register/stack
read and write macros, `Bank`, or the existing `ControlFrame`. Their current interfaces expose the
old state model. Extract a common typed operation only after both frontends need it.

For example, indirect calls should eventually have this shape:

```text
common typed target lookup, type check, and native call
                 ^                         ^
      direct typed SSA arguments   legacy call-record adapter
```

The behavior-preserving extraction must leave emitted native code byte-for-byte unchanged for the
existing diagnostic functions before the direct frontend is added.

## Direct frontend state

The direct frontend constructs semantic state from validated Wasm instructions.

### Operand stack

Maintain a typed operand stack whose entries are Cranelift `Value`s. Ordinary operations pop their
typed inputs and push their typed results. The frontend must represent unreachable polymorphic
stack state explicitly rather than forcing live values into interpreter storage.

### Structured control stack

Maintain a separate direct-frontend control frame for each function, block, loop, if, and supported
exception construct. A frame records at least:

- construct kind;
- entry operand-stack height;
- parameter and result types;
- branch destination and continuation blocks;
- reachability; and
- the typed values or block parameters required by the appropriate branch edge.

Branches use Wasm label depth to select a frame, truncate the operand stack to the frame's entry
height, and pass the construct's declared values as explicit Cranelift block arguments. Genuine
Wasm merge values remain block parameters; unrelated interpreter locations do not.

Control-flow construction is expected to be the bulk of the new frontend. Per-operation Cranelift
emission is largely reusable once it accepts typed operands rather than bytecode locations.

### Locals

Wasm locals remain mutable source-language storage. The initial direct frontend may represent them
with typed Cranelift `Variable`s. This is distinct from representing interpreter scratch registers
as mutable variables. Measure the resulting local block parameters before adding any new local-home
or liveness policy.

### SIMD and references

The direct frontend's type model should include every supported Wasm value kind, including `V128`,
from the start. Individual instruction families may fall back while coverage is incomplete. Do not
add a `V128` bank to the allocated-bytecode frontend as part of this migration.

Do not use the shared 16-byte size of the interpreter's `Value` representation as a reason to give
references and `V128` the same native representation. `V128` is a vector value. Native reference
representations should follow their statically known Wasm reference hierarchy, as described in
"Native reference representation" below.

## Direct compiler input

Do not reuse the current post-allocation `CraneliftInsn` format as the direct frontend's input. Its
sources, destination, synthetic operations, call-record choices, and continuation records encode
the representation being retired.

Define a distinct serialized direct-instruction representation containing semantic instruction
data only. It needs to preserve the information already present in the retained `Instruction`
objects, including:

- opcode and immediates;
- local, global, memory, table, function, type, tag, data, and element indices as applicable;
- block type, end, and else structure;
- branch label depths and complete `br_table` target vectors; and
- memory argument alignment, offset, and memory index.

Variable-length data such as `br_table` targets should use an explicit side region rather than
synthetic continuation instructions. The compile-subprocess input must also provide the module
types and runtime facts required by the supported instructions. Existing function and local type
tables can be reused where their semantics match.

The input batch and native cache format need an explicit frontend or code-flavor discriminator so
direct, allocated-bytecode, and future OSR variants cannot be confused.

## Eligibility and migration

Migration temporarily uses three per-function tiers:

1. direct typed frontend;
2. existing allocated-bytecode frontend; and
3. bytecode interpreter.

Unsupported direct instructions must reject the whole function cleanly and select the next tier;
they must not partially compile a body. Add instruction families generally rather than adding a
workload-specific subset.

Suggested implementation checkpoints:

1. Build the differential native/interpreter harness.
2. Extract `compiler/common.rs` with no generated-code change.
3. Define and version the direct instruction and module-context serialization.
4. Separate clean-entry and OSR-capable runtime publication before a direct body can publish.
5. Add `compiler/direct.rs` with typed operand and structured control stacks, and produce offline
   CLIF and native code for the first structural milestone below without publishing it at runtime.
6. Execute call-free functions from that milestone through a clean fresh-entry adapter, then link
   closed direct-call groups through the clean typed body ABI.
7. Keep mixed-flavor calls on the temporary interpreter boundary, report the frontend that
   actually compiled each function, and replace function-number opt-in with compiler-driven direct
   eligibility plus per-function allocated-bytecode fallback.
8. Complete scalar integer and floating-point numeric operations, conversions, locals, and globals.
9. Complete memory operations, bulk memory, and direct calls.
10. Complete tables, indirect calls, and references.
11. Complete exceptions.
12. Complete SIMD.
13. Re-profile `unzReadCurrentFile`, `AddActiveInteraction`, SHA-512, CoreMark's reported score, and
    the full Wasm benchmark set before considering new state or pressure policies.

Each checkpoint should be independently testable and committed. Do not port a legacy bank,
location-liveness, or synthetic-op optimization merely to preserve existing work.

### First structural milestone

The first direct-generated baseline is function 16,
`sha2::sha512::soft::compress`, in
`~/Repositories/js-benchmarks/WasmRustBench/sha512-bench.wasm`, SHA-256
`301eb9c21fa4eeda2aca6133a2a7c0cfbab55a2ac58daabc2c41c24a87d8d4a8`. It was part of the
historical SHA-512 measurements and exercises the architectural premise without requiring the
whole opcode surface.

Its current instruction inventory is:

- typed parameters and `i32`/`i64` locals using `local.get`, `local.set`, and `local.tee`;
- `block`, `loop`, `br_if`, and function `end`;
- `i32.const`, `i32.add`, `i32.eqz`, `i32.ne`, and `i32.shl`;
- `i64.const`, `i64.add`, `i64.and`, `i64.or`, `i64.xor`, `i64.shl`, `i64.shr_u`, and
  `i64.rotl`; and
- `i64.load` and `i64.store`.

Implement these as general opcode-family support, not as special cases for the named function.
Checkpoint 5 is complete when this pinned function produces valid direct CLIF and native code and
its structural metrics can be compared with the old frontend and Wasmtime. Checkpoint 6 then adds
end-to-end differential execution. This provides a real structured-loop and memory workload before
the broad feature migration, while keeping calls, indirect calls, floating point, exceptions, and
SIMD outside the first lowering slice.

#### Checkpoint 5 result

Commit `613917eb2aa` implements this first lowering slice. The direct frontend consumes the checked
parsed-instruction serialization, rebuilds a typed operand and control stack, represents Wasm
locals with typed Cranelift variables, and emits the pinned function as one clean native body. The
body is deliberately not published or executable through the normal runtime yet: this checkpoint
tests the frontend and generated-code premise, while checkpoint 6 adds the clean-entry adapter and
differential execution.

The final AArch64 native-code comparison is:

| Metric | Direct frontend | Wasmtime 47.0.3 | Allocated-bytecode frontend |
| --- | ---: | ---: | ---: |
| Code bytes | 13,504 | 13,504 | 14,108 |
| Instructions | 3,375 | 3,374 | 3,524 |
| Memory operations | 226 | 226 | 333 |
| Loads | 174 | 173 | 230 |
| Stores | 52 | 53 | 103 |
| Stack-memory operations | 189 | 191 | 218 |
| Branches | 5 | 5 | 16 |
| Calls | 0 | 0 | 2 |

The allocated-bytecode size excludes its 48-byte interpreter adapter. Wasmtime has a VMContext
stack-limit check, while Ladybird obtains linear-memory storage through `Configuration` and the
primitive-storage cage. Equal direct and Wasmtime code size is therefore partly coincidental; the
matching instruction and memory-operation shape is the stronger result.

An instruction-sequence diff confirms that similarity. The comparison was made first using only
mnemonics, then using instruction shapes with physical registers and numeric literals normalized.
This avoids treating different register-allocation names or decimal-versus-hexadecimal formatting
as different lowering. The default Myers diff aligned:

| Comparison | Aligned mnemonics | Aligned normalized instruction shapes |
| --- | ---: | ---: |
| Direct and Wasmtime | 3,356 (99.4% of each body) | 3,355 (99.4% of each body) |
| Direct and allocated bytecode | 3,261 (96.6% of direct; 92.5% of old) | 3,239 (96.0% of direct; 91.9% of old) |

The high old-frontend percentage does not mean that its overhead is insignificant: SHA-512 is a
large repeated round sequence, so most arithmetic mnemonics necessarily align. Its differences
are concentrated in entry and tier-up handling, interpreter-state traffic, spills, and control
flow, which explains the extra 149 instructions, 107 memory operations, 29 stack-memory
operations, 11 branches, and two calls.

For example, the first SHA-512 round contains the same operation sequence in all three bodies.
Direct and Wasmtime are effectively the same native lowering with different physical registers
and stack slots:

One lowering detail was independently measured before retaining it. Forming a linear-memory
address as `(base + zero_extend(index)) + offset`, matching Wasmtime's shape, uses 12 more code
bytes and three more static instructions than `base + (zero_extend(index) + offset)`, but removes
six memory operations and reduces the fixed frame from 272 to 208 bytes. The former shape lets
Cranelift rematerialize offsets near the final stores instead of keeping full derived addresses
live through the large unrolled region.

This checkpoint therefore validates the architectural premise at native-instruction granularity:
given typed parsed Wasm rather than allocated interpreter locations, the same Cranelift backend
produces a SHA-512 body structurally almost identical to Wasmtime's. It does not yet establish
runtime correctness or performance because the direct body cannot be entered until checkpoint 6.

### d3wasm structural milestone (2026-08-06)

The next lowering slice covers the two representative d3wasm functions used throughout the
allocated-bytecode investigation:

- function 1574, `unzReadCurrentFile()`, a primary loading function; and
- function 2445, `idInteraction::AddActiveInteraction()`, a hot lighting function in the heavy
  gameplay scene.

This required general scalar floating-point and conversion lowering, globals, direct calls,
`call_indirect`, `br_table`, and bulk-memory operations in addition to the integer, local,
structured-control, and scalar-memory families from the SHA-512 checkpoint. Both functions now
produce valid direct native code with Cranelift 0.134.3. The clean bodies remain offline and are not
published, so these are structural code-generation results rather than runtime measurements.

The AArch64 comparison uses Wasmtime 47.0.3, which uses the same Cranelift 0.134.3 release. Memory
operations count `ld*` and `st*` instructions, and stack-memory operations are that subset whose

Against the allocated-bytecode frontend, direct lowering reduces `unzReadCurrentFile()` native
instructions by 25.1%, memory operations by 35.6%, and stack-memory operations by 43.6%. For
`AddActiveInteraction()`, the reductions are 28.6%, 42.3%, and 46.4%.

The assembly directly verifies the removal of interpreter-register state traffic. The old native
entry imports the low payload of all eight interpreter registers from the `Value` array in
`Configuration`; after the body, both probes write all eight dirty payloads back and zero all eight
tags. The direct body does neither:

| Verified interpreter-register traffic | Direct frontend | Allocated-bytecode frontend |
| --- | ---: | ---: |
| Entry payload loads | 0 | 8 |
| Exit payload stores | 0 | 8 |
| Exit tag stores | 0 | 8 |

For example, the old `unzReadCurrentFile()` body starts by importing R0-R7 from the 16-byte-spaced
`Value` array. Some imported values are immediately spilled into the native frame:

```asm
ldr x26, [x1]
str x26, [sp, #0x148]
ldr x21, [x1, #0x10]
ldr x25, [x1, #0x20]
str x25, [sp, #0x160]
ldr x28, [x1, #0x30]
...
ldr x26, [x1, #0x70]
```

Its epilogue exports those registers as eight payload/tag pairs:

```asm
str x9,  [x3]
str x10, [x3, #0x8]
str x11, [x4, #0x10]
str x10, [x6, #0x18]
...
str x2,  [x1, #0x70]
str x10, [x1, #0x78]
```

The old body also branches on the resume token and loads or saves interpreter call-record, current
expression, depth, and stack state. The clean direct entry takes `Configuration` directly and its
first loads obtain required linear-memory and global metadata instead; there is no resume-token
branch or R0-R7 import/export sequence:

```asm
ldr x4,  [x0, #0xdd8]
ldr x4,  [x4]
ldr x7,  [x4, #0x68]
ldr x4,  [x0, #0xde0]
ldr x22, [x4]
ldr x28, [x4, #0x8]
ldr x21, [x4, #0x10]
```

This proves that direct lowering removes the old frontend's explicit interpreter-state
import/export and entry-mode setup. It does not prove that every operation removed by the aggregate
counts was interpreter-state traffic. Most of the much larger reduction in `sp`-relative accesses
is native spill and home traffic, consistent with shorter semantic-value live ranges and lower
register pressure but not separately attributable from this static comparison. Direct code still
has ordinary Wasm-local initialization and Cranelift spills. The structural result is therefore
both a directly verified removal of legacy state traffic and a large, separately observed reduction
in native frame traffic, rather than evidence that all frame traffic was legacy state traffic.

The change is not confined to function entry and exit. The silhouette-edge loop previously
identified by profiling as a dominant `AddActiveInteraction()` range was matched by its two facing
byte loads, comparison, and six shadow-index stores in all three current bodies. The current ranges
are `0x13d98-0x13e94` in the allocated-bytecode body, `0xefe8-0xf0b4` in the direct body, and
function-relative `0xe748-0xe810` in Wasmtime. Their loop-local counts are:

| Silhouette-edge loop metric | Direct frontend | Wasmtime 47.0.3 | Allocated-bytecode frontend |
| --- | ---: | ---: | ---: |
| Complete continuing path instructions | 51 | 50 | 63 |
| Complete continuing path memory operations | 18 | 19 | 27 |
| Complete continuing path native-frame operations | 6 | 7 | 15 |
| Complete continuing path linear-memory operations | 12 | 12 | 12 |
| Equal-facing continuing path instructions | 25 | 23 | 30 |
| Equal-facing continuing path memory operations | 7 | 7 | 11 |
| Equal-facing continuing path native-frame operations | 3 | 3 | 7 |
| Equal-facing continuing path linear-memory operations | 4 | 4 | 4 |

The required linear-memory work is unchanged. On the complete path, direct lowering removes twelve
instructions and nine native-frame accesses from the old body and is within one instruction and one
memory operation of Wasmtime. This is direct evidence that the typed frontend changes generated
code on an executed hot loop, not only in interpreter-facing boundary machinery. The remaining
frame accesses are ordinary backend spills, and the counts do not establish runtime speed until the
direct body is published and profiled.

The remaining gap to Wasmtime is 5.9% in instructions for `unzReadCurrentFile()` and 14.3% for
`AddActiveInteraction()`. Call lowering is one concrete contributor: the direct bodies contain 47
and 440 call instructions, versus Wasmtime's 31 and 284. Each current `call_indirect` site emits
its native path plus local cold subtype-check, interpreter-fallback, and trap paths. `memory.copy`
and `memory.fill` deliberately use the existing runtime helpers as a correctness-first stopgap;
from the clean ABI this currently calls `current_interpreter` and then the operation helper. This
preserves `MemoryBuffer` bounds, trap, and storage behavior without introducing a separate libc
relocation and cache-patching design. This is not only abstraction hygiene: `MemoryBuffer` splits
operations at the primitive-storage cage wrap using `contiguous_bytes_from()` and
`contiguous_bytes_before()`, so one unconditional libc `memmove` or `memset` would not implement
the general storage layout correctly. Hoisting or sharing cold indirect-call paths and giving bulk
memory a cleaner direct helper ABI are later code-size and call-overhead work, not prerequisites
for typed direct lowering.

### Checkpoint 6: executable clean fresh entry

The next checkpoint turns the offline structural result into runtime evidence without adding OSR or
temporarily adopting the allocated-bytecode calling convention. Its first end-to-end workload is
the pinned call-free SHA-512 compression function. Implement the boundary generally; do not
special-case that function or its signature.

Generate a separate Cranelift adapter in front of each executable direct body:

1. receive the existing interpreter-handler arguments;
2. load each typed Wasm parameter from `Configuration::locals_base()`;
3. call the clean body with `Configuration*` followed by its typed parameters;
4. convert every typed result to `Value` and append it to the interpreter `ValueStack`; and
5. return after native code has completed the current interpreter frame.

Keep this adapter outside the clean body's Cranelift function. Combine their emitted code only at
the linked-artifact layer, record the clean body's offset, and resolve the adapter-to-body call as a
self relocation before publication. The body slice beginning at `native_entry_offset` must remain
byte-for-byte identical to the current offline output.

Carry the frontend/code flavor through pending installation. A direct artifact publishes:

- its adapter through `cranelift_entry` for fresh interpreter activations; and
- its clean body through `cranelift_direct_native_entry` for direct native callers.

It must not publish `cranelift_osr_entry` or the allocated-bytecode
`cranelift_native_entry`. Allocated-bytecode publication remains unchanged. Trap metadata and code
ownership cover both the adapter and body in the combined mapping, and the fresh entry is published
only after every relocation, permission transition, and instruction-cache operation has completed.

For this checkpoint, select the allocated-bytecode frontend before compiler submission for any
function whose direct lowering can make a cross-function call or enter an indirect-call fallback.
Do not compile such a function with the direct frontend and then silently discard its result,
because that would also discard the current native fallback. The call-free restriction is a staged
publication capability, not an opcode-specific lowering restriction: offline direct compilation of
the d3wasm functions remains useful for structural comparison.

The existing clean direct-call relocation fallback uses the allocated-bytecode call-record ABI and
does not match the clean typed direct-call signature. Do not make it reachable merely to execute
SHA-512. Checkpoint 7 defines the durable typed body ABI and the compatible mixed-function fallback
before call-heavy direct functions can publish.

Add focused differential coverage for:

- zero and multiple parameters across each supported scalar type;
- declared-local zero initialization;
- zero, one, and multiple typed results at the adapter unit level, even while runtime eligibility
  still excludes instruction families needed by some signatures;
- native explicit and fault-based traps reaching interpreter fault recovery;
- equivalent direct and interpreter results and observable state; and
- fresh direct execution leaving the successful OSR-transfer counter unchanged.

After correctness tests pass, run the SHA-512 benchmark with parse, compilation, and execution
phases reported separately. Compare workload execution, generated-body bytes, fixed frame, native
instruction counts, total load time, compiler wall time, and peak compiler memory. This is the first
runtime test of the new representation; the earlier structural result alone does not establish an
execution-speed improvement.

#### Checkpoint 6 result

### Retirement of the allocated-bytecode frontend

The three-tier arrangement is a staged rollout, not the intended final architecture. The
allocated-bytecode frontend receives correctness fixes and only the minimum interoperation work
needed to unblock migration. Do not add new optimization policy, opcode-family implementations, or
permanent abstractions to it. In particular, the direct frontend's typed state model and durable
native ABI must not conform to interpreter allocation locations merely to prolong mixed-flavor
operation.

Retire the old frontend in explicit stages:

1. Use it as the per-function native fallback while direct instruction-family coverage grows.
2. Stop using it for fresh entry once the direct frontend covers every function the old frontend
   could compile and the direct path has passed differential, specification, and workload tests.
3. Keep it only as a temporary OSR compiler while the direct OSR path or another production tier-up
   design is completed and validated.
4. Delete it once fresh entry, native calls, indirect calls, incremental publication, the native
   cache, and interpreter-to-native tier-up no longer depend on allocated-bytecode compilation.

#### Type-index control signatures

The first retirement blocker was not merely support for a different block-type encoding. A
type-index block denotes a complete function type with parameters and results. On entry, `block`,
`loop`, and `if` consume the parameter tuple and make it available to the body. Branches to a
`block` or `if` label carry the result tuple, while branches to a `loop` label carry the parameter
tuple for the next iteration. An `if` consumes its condition before its parameters and makes the
same parameter values available to both arms; when the encoded `else` is absent, the implicit empty
arm passes the parameter tuple to the continuation as its result tuple.

The direct control frame now records those two tuples separately. Loop headers have typed
Cranelift block parameters and fresh entry and back edges pass the same typed argument list.
Continuations retain only the result tuple. Existing direct OSR checkpoints remain compatible:
validation only marks a loop tier-up eligible when its block parameter list and surrounding operand
stack are empty, and the compiler rejects inconsistent serialized checkpoint metadata rather than
constructing an OSR edge without the required loop arguments.

#### Native reference representation: preserve the typed hierarchy

Ladybird's interpreter-facing `Value` currently stores references in a 16-byte low-word/high-word
encoding. The low word contains a function, extern, or exception store address, an `i31` payload,
or a `GC::Cell` pointer. The high word identifies the runtime reference variant, except that a
function reference stores its defining `Module*` there. This is the canonical interpreter and
runtime representation; it is not a requirement that native SSA carry every reference as one
16-byte `I8X16` value.

An initial experiment proposed one universal tagged `i64`, provisionally named
`Wasm::TaggedReference`. Its payload retained `FunctionAddress`, `ExternAddress`, and
`ExceptionAddress` store indices, stored `i31ref` inline, and compressed `GC::Cell` pointers as heap
region offsets. Unit tests proved that all current 16-byte `Value` reference variants could round
trip through that encoding. Direct lowering could also encode and decode it with integer
operations, except that reconstructing a non-null function reference still required recovering its
defining `Module*` from the store.

That experiment answered the size question but exposed a more important representation question:
a store index is stable and serializable, but retaining it also preserves the runtime lookup that
native code normally wants to remove. A universal dynamic tag similarly spends work rediscovering
which reference hierarchy the validated Wasm type already identifies. The experiment is therefore
parked rather than adopted as the durable representation.

The preferred direction is hierarchy-specific native representations carried alongside their
validated Wasm types:

- function references use a stable `CallableMetadata const*`, with null represented by a null
  pointer;
- structure and array references use stable `GC::Cell*` values;
- `i31ref` remains an inline integer;
- the `anyref` and `eqref` hierarchies use a compact tagged union only where the source type can
  genuinely contain multiple runtime forms;
- host `externref` retains its external-reference handle until the JS/Wasm boundary has a durable
  resolved representation; and
- exception references retain their store address until exception storage has stable addresses or
  a separate stable descriptor.

`Store::m_callable_metadata` already owns each descriptor through `NonnullOwnPtr`, so vector growth
moves owners but not descriptors. `CallableMetadata` already records the `FunctionAddress`,
defined type, module instance, compiled entry, and call arities, and table storage already caches the
same pointer for `call_indirect`. This makes it a natural function-reference identity for native
code rather than a new compatibility object. Interpreter materialization still needs the defining
`Module*` currently stored in `Value`'s high word; either the stable descriptor must expose that
boundary metadata or conversion must recover it only when leaving native code.

Do not compress arbitrary C++ pointers merely to reserve universal tag bits. LibGC heap pointers
can be compressed because the collector explicitly reserves and aligns its heap region; no
equivalent invariant currently exists for `CallableMetadata`, host-reference storage, or exception
storage. When the static Wasm hierarchy permits a raw pointer, retain the full pointer width.

The direct frontend should therefore retain semantic reference types on its operand stack and
control edges even though Cranelift represents each current form as an integer or pointer-sized
value. Subtyping-compatible edges can share a representation, while a real hierarchy conversion
performs the required boxing or tagging. Convert to the existing 16-byte `Value` only at
interpreter, legacy-helper, and persistent-runtime storage boundaries. Every conversion must
preserve the runtime distinctions required by null checks, equality, casts, conversions, and
indirect or reference calls.

These representations do not require Cranelift stack-map spills for Ladybird's current
conservative, non-moving collector. LibGC uses `setjmp()` to scan saved register state and also
scans the active native stack. At a synchronous helper call, the platform ABI requires a live
value to reside in callee-saved state or a spill slot; both locations are covered. A compressed
GC-object payload must use LibGC's recognized cell pattern, while an uncompressed `GC::Cell*` is
already a conservative root. Do not force every live reference to the stack merely because it may
otherwise occupy a CPU register.

Validate each hierarchy before making it part of the durable native reference ABI:

- round-trip each native representation through `Reference` and `Value` at every supported
  boundary;
- test reference equality, null families, casts, and `extern.convert_any`/`any.convert_extern`;
- keep a live GC reference across an allocating helper call and force collection;
- test function-reference lifetime and identity across modules, imports, globals, and tables;
- verify that `CallableMetadata` addresses remain stable while the store allocates more functions;
- inspect generated code to confirm references use GPRs and avoid 16-byte state traffic; and
- compare reference-bearing direct calls with interpreter fallback at the same semantic boundary.

The first function-reference experiment covers the interpreter-callee-to-direct-caller seam. A
direct `call_indirect` whose result belongs to the function-reference hierarchy uses a nullable
`CallableMetadata const*` result. When the target is still interpreted, the existing indirect-call
fallback helper resolves the interpreter's `FunctionAddress` result to its stable descriptor before
returning; this does not add another native-to-C++ transition. Both typed and untyped null function
references become a null pointer. The direct native-target arm has the same pointer-sized return
slot and joins without a representation conversion, but no reference-returning function is yet

results, and reference-bearing direct function signatures remain rejected rather than inheriting
this representation accidentally.

bump the cache format before measuring browser workloads; an old cached body must not silently
preserve the frontend being tested for removal. Keep direct OSR publication enabled and measure
native compilation separately from execution, workload scores, loading time, and frame rate.

Deletion includes its serialized compiler input, banks and location-state reconstruction,
synthetic-instruction lowering, legacy native ABI, cross-flavor relocation selection, adapters, and
OSR-only compiler path. Retain only infrastructure that is independently required by the direct
frontend or runtime, such as trap lowering, relocation representation, alias regions, publication,
and cache plumbing.

Benchmark and profile the retirement checkpoint against the old frontend, but do not retain the
old frontend as a runtime option solely for comparison. The interpreter remains the startup and
cold-function tier and the correctness oracle; removing the old native frontend does not remove the
bytecode interpreter.

#### Fresh-entry retirement experiment (2026-08-29)

Fresh compilation is now direct-or-interpreted. A function whose parsed instruction stream cannot
be serialized for the direct frontend is not submitted to the compiler process. If direct
compilation rejects a submitted function, the compiler omits that function from its output instead
of retrying the allocated-bytecode frontend. The allocated-bytecode compiler implementation remains
in the tree while this experiment is measured, but it has no fresh-compilation caller.

Both sides of the compiler-process boundary enforce the policy. The Rust worker rejects an input
that requests allocated-bytecode fresh compilation, and the C++ consumer rejects a compiled output
whose frontend is not direct. Native cache format version 33 invalidates earlier mixed-frontend

stale cached allocated body therefore cannot make the retirement experiment appear successful.

#### Direct-to-direct indirect-fallback call records (2026-08-29)

The fresh-entry retirement experiment exposed a missing interpreter-boundary setup in direct
native callees. A direct function entered from the interpreter inherits a call record allocated for
that function, but a clean native-to-native call deliberately creates no interpreter frame. If the
callee's `call_indirect` could not resolve a direct native target, its cold fallback nevertheless
loaded `Configuration::call_record_base` and marshalled arguments through it. That pointer could be
null when the caller itself needed no call record.

The d3wasm failure was captured before changing the lowering. LLDB stopped on an
`EXC_BAD_ACCESS` with `FAR = 0`, `x0 = 0`, and generated function 6123, `emloopcb`, executing:

```text
ldr x0, [configuration, call_record_base_offset]
mov w1, argument
str x1, [x0]
```

Disabling native-to-native calls avoided the failure, while forcing atomic rather than incremental
compilation did not. Delaying each batch between compiler return and publication made the normal
execution interleaving long enough for LLDB to attach; the delay was diagnostic and did not cause
the null pointer.

The direct frontend now creates call-record storage only on the cold indirect-call fallback path.
It saves the previous base and stack top, publishes the old top as the temporary base, advances the
top by exactly the number of marshalled `Value` entries, calls the interpreter bridge, and restores
both fields before either returning the result or raising the reported trap. A resolved native
indirect call does not execute this setup.

A focused regression covers the relevant execution shape: a fresh direct wrapper with no call record
directly calls another direct body, whose one-argument `call_indirect` falls back to an
interpreter-only target. With the old lowering the invocation did not complete and had to be
interrupted; with the fix it returns 42. All 29 `TestWasmExecution` cases pass, and a cache-free
d3wasm run with the three-second publication delay completed its 45-second startup window past the
original failure point without a crash.

Do not delete the allocated-bytecode implementation solely from these coverage results. First run
the browser loading, frame-rate, compilation-time, execution-time, and compiler-memory comparisons
listed above. If those results are sound, the next checkpoint is mechanical removal of the retired
fresh path and its cache, output, relocation, adapter, and test scaffolding; unsupported functions
continue to use the bytecode interpreter.

## Differential verification harness

Build the verification harness before the direct frontend. A wrong reaching definition, block
argument, stack truncation, or conversion can silently miscompile rather than crash.

`LADYBIRD_CRANELIFT_COMPILER=/usr/bin/false` already provides an interpreter-only oracle. The
harness must run equivalent inputs with native compilation enabled and disabled, then compare:

- returned values, including exact integer and deterministic floating-point bit patterns;
- traps and trap reasons;
- mutable globals;
- linear-memory contents and size;
- table-visible effects;
- imported function calls and observable host effects; and
- behavior across repeated calls and fresh instances.

Existing expected-result tests remain valuable but are not themselves differential. The harness
should make it easy for every newly migrated instruction family to run in both modes. It must avoid
native cache reuse when a cold compilation is required and must distinguish harness wall time from
the program's measured compilation and execution phases.

### Randomized differential coverage

Curated differential cases establish readable intent but do not explore enough combinations of
operand-stack shape, reachability, nested control flow, branch arity, and state mutation. Add a
wasm-smith-style valid-module generator to the same harness. Each generated case must:

1. be limited to instruction families that the direct frontend claims to support;
2. use a recorded seed and bounded module, memory, table, call-depth, and execution limits;
3. prove that each function under test actually used the direct frontend rather than silently
   falling back;
4. execute equivalent fresh instances through the direct compiler and interpreter-only oracle;
5. compare results, traps, memory, globals, tables, imports, and repeated-call effects using the
   same floating-point policy as curated tests; and
6. retain the seed and reduce every mismatch to a focused permanent regression test.

Parser and validator fuzzing are separate concerns. This generator should primarily produce valid
modules so its budget exercises typed lowering, structured control flow, and execution. As direct
coverage grows, expand the generator's enabled feature set at the same checkpoint as each complete
instruction family.

### Floating-point and relaxed-result policy

The local WebAssembly specification states that some numeric operators are non-deterministic
because they may return one of multiple NaN values. NaN propagation requires a canonical payload
when all NaN inputs are canonical (including no NaN inputs); otherwise any arithmetic-NaN payload
is permitted outside the deterministic profile. `fneg`, `fabs`, and `fcopysign` are excluded from
that propagation rule and preserve or change specified sign/payload bits. Relaxed SIMD adds further
instruction-specific result sets.

The broad differential comparison must therefore not require identical NaN payloads whenever the
instruction semantics permit different payloads. At minimum, it should classify both results as
valid members of the permitted NaN class. Exact comparison remains required for bit-preserving
operations, reinterpretation, explicitly pinned payload tests, non-NaN values including signed
zero, and state whose bits are observed through integer reinterpretation or memory.

An end-to-end harness may not know which operation produced a returned or stored NaN. Its test
format therefore needs an explicit comparison policy: exact bits by default, with spec-derived NaN
or relaxed-result matching only for tests that opt into it. The core specification tests remain the
authority for canonical-versus-arithmetic NaN constraints; globally canonicalizing every NaN would
hide invalid results as well as suppress false differences.

## Cross-flavor calls

Mixed direct, allocated-bytecode, and interpreted functions must call one another correctly. That
is a hard migration invariant. It does not imply that the direct frontend must permanently adopt
the current native body ABI.

The current ABI is only partly representation-neutral:

- every body receives interpreter and configuration pointers plus an entry/resume token;
- functions with at most eight parameters receive typed arguments;
- functions above that cutoff receive a pointer to call-record locals; and
- functions with more than one result are rejected from native compilation.

Sharing that ABI between both native frontends would make cross-flavor direct calls simple, and it
would not constrain the direct frontend's internal typed SSA. It would, however, preserve
interpreter-derived entry arguments and the high-arity call-record convention in direct-generated
call sequences. The existing ABI must therefore not become permanent merely because it is moved to
`common.rs`.

The possible migration boundaries are:

1. Define a durable typed native body ABI and update the old frontend to consume it. The old
   frontend may need temporary marshalling from call-record storage for high-arity calls. Define
   multi-value returns in this ABI from the start rather than carrying forward the old frontend's
   one-result restriction; individual frontends may still fall back until their adapters support
   the complete result convention.
2. Give direct functions a clean body entry plus a legacy-compatible adapter, and provide the
   reverse boundary needed when direct code calls an old body. Adapters isolate legacy state but
   are deliberate migration code. Relocation patching then selects the symbol by caller flavor:
   old-frontend callers target the legacy adapter, while direct callers target the clean body.
   That selection belongs to the shared ABI/relocation layer, not either frontend.
3. During early bring-up, prohibit direct cross-flavor relocation patching and use the existing
   interpreter/helper boundary for mixed calls. This avoids ABI commitment but distorts call-heavy
   performance and cannot be the final mixed-module path.

The first executable SHA-512 milestone was stricter than option 3: it published only closed direct
groups and therefore had no cross-flavor native relocation. The current migration uses option 3:
direct-to-direct relocations target the clean body, while mixed calls cross the existing interpreter
mechanism through cold local fallback adapters. The old frontend has not been changed to consume a
new durable ABI merely to extend its lifetime. Those adapters and flavor-sensitive fallback choices
are deleted with the allocated-bytecode frontend if the direct design continues to prove fruitful.

The dependency direction remains important: neither frontend should privately define the eventual
body ABI. Once selected, a shared ABI module owns signatures, entry symbols, and relocation
contracts. Per-flavor ABI divergence is prohibited unless an explicit adapter owns the boundary.
ABI experiments then update the shared contract and cache version atomically rather than leaking
legacy locations into direct lowering.

## OSR and code flavors

The first direct frontend should produce clean entry-only code. It does not need to solve direct
OSR before demonstrating the generated-code benefit.

### Fresh interpreter entry into a clean direct body

Interpreter compatibility does not require adding interpreter state to the clean direct body. The
interpreter has already created the activation's `Frame`, initialized its locals, and installed the
compiled-fault recovery context before it decides whether to enter native code. A separate, small
entry adapter can therefore:

1. receive the existing interpreter-handler arguments;
2. load the function parameters from `Configuration::locals_base()` according to the function's
   fixed local-type table;
3. call the clean direct body with `Configuration*` followed by typed Wasm parameters;
4. convert every typed result to `Value` and append it to the interpreter `ValueStack`; and
5. return after native code has completed the current interpreter frame.

Generate this adapter as a separate Cranelift function, not as an entry block in the clean body.
Publish it through `cranelift_entry` for fresh interpreter calls, while direct native callers use
`cranelift_direct_native_entry` and never execute the adapter. This preserves byte-for-byte clean
body code generation and localizes interpreter payload conversion to the actual boundary.

The allocated-bytecode adapter already demonstrates the surrounding frame, fault, trap, and result
machinery. The direct adapter is narrower because it imports parameters rather than interpreter
scratch-register state and has no resume-token dispatch. Scalar leaf functions are the first
bounded milestone. Complete support must also define typed multi-value result marshalling, `v128`
payload handling, reference rooting, and the behavior of calls whose target is not yet available
through the direct ABI.

### Runtime publication capability

Runtime metadata now distinguishes:

- an entry capable of starting a fresh activation;
- an entry capable of resuming the current bytecode activation at a checkpoint;
- the allocated-bytecode native body used by legacy compiled callers; and
- the clean direct native body.

These are acquire/release-published through `cranelift_entry`, `cranelift_osr_entry`,
`cranelift_native_entry`, and `cranelift_direct_native_entry`. Fresh calls select only the fresh
entry, while `synthetic_tier_up` polls only the OSR-capable entry. Seeing only a clean entry keeps
interpreting. This permits a persistent clean direct body and a temporary OSR body to coexist
without making a polling checkpoint enter an entry-only adapter with a checkpoint token.

The successful-transfer counter continues to count only an actual checkpoint-to-OSR handoff, not
clean publication or an OSR request. Its trace identifies the function and checkpoint. The one-way
regression test covers the two-flavor seam:

1. publish a clean-only entry while an activation is interpreting;
2. prove a checkpoint does not enter it or increment the transfer counter;
3. publish an OSR-capable entry and prove exactly one transfer;
4. prove the following fresh call uses clean code without another OSR transfer; and
5. keep the OSR code alive until the transferred activation returns.

The existing seam test exercises this with the allocated-bytecode adapter: it publishes a fresh
entry while withholding the OSR entry, proves that the checkpoint continues interpreting, then
publishes the OSR entry and proves the one-way handoff. The counter increment is on the successful
OSR path rather than the fresh-entry poll.

### Tier-up checkpoint state

Wasm locals are function-scoped indexed storage, not lexically scoped variables. Their types are
fixed for the lifetime of the activation and are already available to the direct frontend from the
function signature and serialized declared-local types. Duplicating all local types at every
checkpoint would therefore add no information. The useful per-checkpoint fact is which typed
locals are live into that continuation.

The current validator deliberately restricts tier-up eligibility to loop headers with no loop
parameters and an empty operand stack. The bytecode generator inserts `synthetic_tier_up`
immediately after only those eligible loop headers. Consequently, the first direct OSR path does
not need to reconstruct R0-R7 or `ValueStack` temporaries: they contain no live semantic operand at
the transfer point. Its input state consists of canonical Wasm locals plus normal runtime state in
`Configuration`.

This empty-stack restriction is an important correctness boundary, not merely a temporary
implementation convenience. Resuming with a non-empty operand stack would require every
checkpoint to describe the precise typed stack shape and map each live operand to its interpreter
`ValueStack` location. The direct frontend would then have to reconstruct those values through
nested control flow and merge them into native SSA alongside the locals. Empty-stack loop headers
avoid that state class entirely while still covering natural hot points: loop-carried Wasm state is
commonly held in locals. Broaden checkpoint eligibility only if profiles demonstrate important
loops that this restriction excludes.

Fresh interpreter-to-native entry is the smaller form of the same state import. The interpreter
frame already contains the function arguments, while every declared local still has its
Wasm-defined default value. The fresh adapter loads the typed arguments from the frame and the clean
body defines declared numeric locals as typed zero constants. There is no continuation merge and
no checkpoint liveness question because these definitions form the function's initial state and
dominate the body. A mid-function OSR edge cannot make that assumption: its locals may contain
arbitrary values produced by the interpreted prefix.

Preserve an explicit checkpoint descriptor while the validated parsed instruction and generated
interpreter dispatch are both available:

```text
TierUpCheckpoint {
    checkpoint_id,
    interpreter_dispatch_index,
    parsed_loop_instruction_index,
    live_local_indices,
}
```

The function-wide local-type table supplies each live local's type. Compute `live_local_indices`
with backwards dataflow over the parsed Wasm CFG; bytecode location access counts and write sets are
not substitutes for edge liveness. A local is live into a checkpoint when some continuation path
can read its current value before overwriting it. The resume adapter therefore loads and defines
only that subset. This avoids activation-memory loads, resume-edge SSA definitions, merge
parameters, and register pressure for dead locals; omitting a genuinely live local would instead
be a miscompile. A bitmap is sufficient for the indexed local set. If checkpoint eligibility later
expands, the descriptor must also carry the typed operand/control-stack live-ins and, for
non-defaultable references, the validator's definite-initialization state.

When a function is compiling while an interpreter activation is already running:

1. Publish the clean direct body for future calls and store only that flavor in the normal cache.
2. If a live activation can benefit, request an allocated-bytecode OSR flavor using the existing
   checkpoint and interpreter-location machinery.
3. Allow that activation to transfer into the temporary flavor.
4. Retain the temporary code until every transferred activation has returned, then reclaim it.
5. Discard an unused result when no interested activation remains.

This policy preserves the demonstrated d3wasm tier-up staircase without permanently charging fresh
or cached calls for OSR dispatch and resume predecessors.

The expected replacement for the temporary allocated-bytecode OSR compiler is a direct OSR
variant. It is compiled separately from the persistent clean body, is not stored in the normal
native cache, and is requested only while an interpreting activation can use it. Its cold resume
adapter receives `Configuration` and the checkpoint identity, selects the corresponding resume
entry, loads only the checkpoint's live typed locals from `Configuration::locals_base()`, and
continues at the native loop header. Native completion completes the interpreter frame; there is no
tier-down path and no need to synchronize locals back to interpreter storage.

The first correct direct OSR variant may compile the complete function with both fresh and resume
predecessors even if only the resume entry is published. The direct frontend currently emits
structured control flow in one pass. A continuation entered inside a nested loop may later branch
to an enclosing loop header encountered earlier in the instruction stream, so simply omitting the
prefix does not necessarily emit the complete reachable cyclic CFG. Paying resume merges in a
temporary OSR flavor is acceptable because it does not affect clean cached code. A later two-pass
CFG/control plan can produce a narrower OSR-only variant if measurements justify it.

#### First direct OSR variant implementation shape

Compile the first direct OSR variant as a separate Cranelift function using the interpreter-handler
ABI already used by `synthetic_tier_up`. The handler arguments provide `Configuration` and the
interpreter dispatch position identifying the checkpoint. Do not add an OSR token, interpreter
pointer, or canonical-local arguments to the persistent clean body's typed ABI. The direct
instruction lowering should be shared between the clean and OSR flavors, with the entry and
completion strategies selected outside the per-operation lowering rather than by copying the
instruction switch.

Before emitting the function body, validate and index every serialized checkpoint:

- checkpoint identifiers are unique and stable;
- the parsed instruction index names an eligible `loop` in the direct instruction stream;
- the interpreter dispatch index is the corresponding `synthetic_tier_up` position; and
- every live-local range and local index is in bounds, ordered, and free of duplicates.

Pre-create the native loop-header block for every checkpoint before emitting the entry dispatcher.
This allows the cold resume blocks to target loop headers that the one-pass structured-control walk
has not reached yet. When the walk later encounters the parsed `loop`, it must reuse the pre-created
block rather than create a second header. Keep the header unsealed until all normal fresh-entry,
resume, and back-edge predecessors have been emitted.

The OSR function's common entry block receives `Configuration` and constructs any runtime-state
values that generated instructions use directly, such as memory, table, and global-instance bases.
Those values must dominate both the fresh and resume paths; a value created only on the fresh path
cannot safely be referenced after a resume edge. The entry then dispatches as follows:

1. A zero entry token selects an internal fresh path. It imports the function parameters from the
   interpreter frame and gives declared locals their Wasm default values, making the complete
   function CFG reachable during the first implementation even though this entry is not published
   for fresh calls.
2. Each known checkpoint selects a cold resume block. That block loads
   `Configuration::locals_base()`, imports only the checkpoint's live locals using the function-wide
   type table, defines their native SSA variables, and jumps to the pre-created loop header.
3. An unknown non-zero checkpoint is rejected rather than silently entering the function at the
   wrong position.

The exact live-local set is therefore consumed only on the cold resume edge. Dead locals receive no
resume definition and cannot create activation loads or resume-induced merge parameters. A local
that is defined before every use after the checkpoint needs no imported value; a local that may be
read first must be imported on every resume predecessor that can reach that use.

Because `synthetic_tier_up` transfers ownership of the current interpreter activation, the OSR
function completes through the interpreter boundary rather than returning typed results to a native
caller. Every Wasm return path must marshal its typed results into `Value` entries at the current
`ValueStack` top, advance the top exactly once, and return through the handler ABI. It does not
write locals back: native completion completes the frame, and this design has no tier-down path.
Traps continue through the existing compiled-fault recovery mechanism, with the temporary mapping's
trap table retained for at least as long as any transferred activation can execute it.

Compile and retain this OSR artifact independently from the normal direct result. Do not serialize
it into the native cache, publish it as the clean fresh entry, or concatenate it with the persistent
clean mapping merely to reuse installation code. As a regression invariant, compiling checkpoint
metadata and an OSR variant must leave the clean body's CLIF, native bytes, relocations, and traps
unchanged.

#### Compiler-only direct OSR checkpoint (2026-08-11)

Commit `5a5ee20a742` implements the first compiler-only direct OSR body. It deliberately stops
before the compiler subprocess returns the second artifact and before the runtime maps or publishes
it. The checkpoint therefore proves that the direct frontend can construct the required native CFG
without changing the persistent clean body; it does not yet prove an interpreter-to-direct
transfer.

The clean and OSR flavors share one instruction-lowering walk. Flavor-specific behavior is kept at
the function boundary:

- the clean flavor retains its typed body ABI and typed returns;
- the OSR flavor uses the existing interpreter-handler ABI, with `Configuration` and the raw
  interpreter dispatch position taken from the established handler arguments;
- runtime values needed by the body are constructed in the common entry so they dominate both
  fresh and resume paths;
- every checkpoint loop header is pre-created and reused when the structured-control walk reaches
  the corresponding parsed `loop`;
- a cold resume block imports only the checkpoint's exact live-local set from
  `Configuration::locals_base()` and jumps to that header; and
- every OSR return path appends the typed results to the interpreter `ValueStack` and returns from
  the handler, without writing locals back.

The first variant retains the complete function CFG. Entry token zero selects an internal fresh
path that imports parameters and zero-initializes declared locals; a known non-zero token selects a
checkpoint resume block; and an unknown token traps. The fresh path is an implementation device for
building and testing the complete CFG and is not a second published fresh entry.

The compiler validates contiguous checkpoint identifiers, unique interpreter dispatch positions,
the parsed loop index and duplicate loop mappings, every flattened live-local range, local bounds,
and strict live-local ordering. The durable descriptors are constructed at the point where the
bytecode generator inserts `synthetic_tier_up`, so their dispatch positions originate from the
actual generated stream. The standalone Rust lowering API does not receive that allocated stream,
however, and therefore cannot independently prove that the serialized dispatch position still
names `synthetic_tier_up`. The subprocess integration must perform that final cross-check while it
has both representations; publication must not rely only on the descriptor's integer value.

Direct calls in the OSR body retain the same typed direct-call lowering and interpreter fallbacks
as the clean body. The fallbacks are appended to the temporary artifact and its relocations and trap
offsets are adjusted independently; the clean and OSR mappings are not concatenated. The OSR
artifact reports entry offset zero because its public entry is already the interpreter-handler
entry rather than a clean typed body behind a separate adapter.

The regression test compiles the same function before and after attaching checkpoint metadata and
requires identical clean native bytes, relocations, and traps. It then compiles the OSR flavor with
two live typed locals and verifies that it produces an independent native artifact. Validation for
this checkpoint was:

- all 12 Rust unit tests passed;
- Clippy passed with `-D clippy::all`;
- the release `TestWasmExecution` target built successfully; and

#### Direct OSR transport-and-retention checkpoint (2026-08-11)

Commit `1f1e1167234` extends the compiler subprocess result so one function can return a normal clean
artifact plus an optional OSR artifact. Both artifacts receive independently checked code,
relocation, trap, and entry-offset ranges. The clean artifact is written first, so an unavailable
OSR output region cannot discard an otherwise valid clean compilation. An OSR compile, output,
link, or finalization failure likewise retains the clean result.

After the 2026-08-26 rebase, this result uses master's compact out-of-process transport. C++ creates
separate compiler input and output buffers. The input serializes `RuntimeLayout` but no
process-specific helper addresses; the small `cranelift-compiler` executable only maps the buffers
and delegates to `serialized::compile_serialized_buffer()`. Rust packs the clean and optional OSR
artifacts into the compact output, and the parent resolves helper relocations in unpublished
mappings before finalizing and publishing them. The direct OSR design therefore survives the
transport change without restoring the former in-place buffer or exposing parent-process addresses
to the compiler process.

The subprocess now performs the final cross-representation validation omitted from the standalone
Rust lowering API: every serialized interpreter dispatch position must be in bounds in the
allocated instruction stream and must name `synthetic_tier_up`. The Rust regression test constructs
the smallest valid allocated stream, derives rather than hard-codes the checkpoint position, and
also verifies that replacing the named instruction with `nop` rejects the OSR compile.

The parent maps and links the OSR artifact separately from the clean body, records a separate code
and trap range for fault recovery, and retains both mappings through a move-only module-owned
`CraneliftCodeOwner`. This replaces the previous one-handle-per-function ownership assumption
without exposing the mapping implementation in `Types.h`. The retained OSR handler is deliberately
not written to `cranelift_entry`, `cranelift_direct_native_entry`, or `cranelift_osr_entry` in this
checkpoint.

Only the clean artifact participates in native-cache capture. The execution regression test first
compiles a direct function containing one eligible loop, verifies that its clean and retained OSR
mappings are distinct while `cranelift_osr_entry` remains zero, and captures the cache blob. It then
installs that blob into a fresh module and verifies that the clean direct body is restored but all
OSR code and trap fields remain empty. This proves cache exclusion independently from publication.

#### Direct OSR traps and multi-value results (2026-08-11)

Commit `ad20bb93d82` exercises the next two interpreter-boundary requirements. The checkpointed
function now returns an `i32` and an `f64` after a successful OSR transfer, then a forced interpreted
entry takes the same OSR mapping and executes a native `unreachable`. The test requires the second
transfer count, the Cranelift `unreachable executed` trap, and the two successful result payloads
from both OSR and clean entry. This also exercises fault lookup through the separately retained OSR
code and trap ranges.

The shared validator previously rejected every multi-result function before selecting a frontend,
even though the direct clean and OSR adapters already support multiple scalar results. That
allocated-bytecode restriction is removed from top-level function eligibility. Calls *to* a
multi-result function remain separately restricted because their mixed interpreter fallback does
not yet support multiple results.

The result test exposed another boundary-only mismatch: C++ `Value` sign-extends every 32-bit
payload into its low 64-bit storage word, while the shared native helper zero-extended `i32` and
`f32`. Both cases now sign-extend at native/interpreter boundaries. The differential fixture makes
its multi-result function directly compilable and compares a negative `i32` plus an `i64`
bit-for-bit against interpreter execution. `Wasm::Result` remains in its established top-of-stack
first order; declaration-order conversion at the JS boundary is separate work.

#### Concurrent direct OSR publication (2026-08-11)

Commit `48b7ae25364` adds an execution race without changing production publication. The fixture's
first loop-header checkpoint necessarily observes zero because its guarded compile import is called
later in the first loop body. That import starts `start_cranelift_compilation()` on a real
`Threading::Thread` and returns immediately. Subsequent interpreter back-edges therefore race their
acquire-loads against background mapping, linking, ownership transfer, metadata installation, and
the final release-store of `cranelift_osr_entry`.

The test uses a five-million-iteration bound so the interpreted activation remains live until the
compiler subprocess publishes, then requires exactly one OSR transfer, successful thread join, and
the exact two-result output from the resumed activation. It passed ten consecutive focused runs.
Because installation already retained the mapping and trap table before release-publication, no
production change was needed.

The restricted one-way mechanism is now covered for scalar locals, an empty operand stack,
multiple scalar results, native traps, cached clean-body separation, mapping lifetime, and
concurrent publication. Checkpoint eligibility, temporary-artifact reclamation, and compilation
policy remain separate decisions rather than correctness prerequisites for the current path.

Temporary OSR code also requires the runtime to own more than one native mapping and trap range for
one function. The first correctness implementation may retain every published OSR artifact until
module destruction. Safe early reclamation, request cancellation, and generation replacement are
later policy work and must not precede correct fault lookup and activation lifetime.

This restricted empty-stack OSR path is materially smaller than general OSR. Supporting loop
parameters, a non-empty operand stack, arbitrary control positions, exceptions, or live references
would require typed operand/control-stack maps, reference rooting, and additional validator state.
Do not broaden checkpoint eligibility until the restricted path is correct and measured.

Suggested interpreter-compatibility sequence:

1. Generate the fresh-entry adapter and execute a scalar leaf direct function end to end.
2. Complete the direct-call ABI and mixed-call fallback needed to publish call-heavy functions.
3. Persist stable checkpoint descriptors and compute exact local live-ins.
4. Compile an uncached full-function direct OSR variant for the existing empty-stack checkpoints,
   retaining its mapping until module destruction.
5. Preserve byte-for-byte clean body output and verify fresh execution, one-way tier-up, traps,
   multiple results, and concurrent publication independently.
6. Only then consider a two-pass OSR-only CFG, earlier reclamation, or broader checkpoint
   eligibility.

## Design review: incremental compilation, publication, and interpreter independence

The direct frontend and OSR design were reviewed against concerns about lost compilation
parallelism, live-code patching, interpreter viability, and how to attribute the remaining gap to
Wasmtime. The concerns identify measurements and invariants that the migration must preserve, but
they do not require coupling native value identity back to interpreter allocation.

### Separate compilation scheduling from incremental publication

The current incremental plan groups the module's call graph into strongly connected components and
submits dependency-ordered batches of at most 512 functions or 100,000 allocated-bytecode
instructions. Batches are submitted synchronously: the parent waits for one compiler subprocess,
installs its results, and only then submits the next batch. Inside each subprocess, compilation is
still parallel. The compiler uses `available_parallelism()` workers and partitions the batch into
function-count-based chunks.

Incremental tiering has therefore not removed parallel compilation, but it can reduce its
effectiveness through small dependency-frontier batches, load imbalance between differently sized
functions, repeated subprocess startup, and sequential batch waves. It also changes publication
from one whole-module event to incremental batch installation. The observed interpreter-to-native
staircase demonstrates the benefit of early publication, but does not establish that ordering
compilation by dependency is the best way to provide it.

Call-graph dependencies constrain final linking and publication, not Cranelift compilation. A
preferred future shape is:

```text
all eligible functions compile in one parallel worker pool
                         |
                         v
completed relocatable artifacts enter a result queue
                         |
                         v
one serial linker/publication path installs ready components
                         |
                         +-- unresolved functions remain interpreted
```

Compilation may proceed across the whole module while the linker retains a caller until its direct
callees have stable addresses, installs a recursive component together, or selects a permanent
fallback boundary. This preserves early native availability without turning link order into compile
order. The current separate-buffer compiler protocol returns only after every function in a submitted batch
has finished, so streaming completion requires a transport/protocol change rather than only a new
batch-size constant.

Measure the current dependency-batched policy against a single whole-module submission before
changing it. Record compiler wall time, compiler CPU time, CPU utilization, subprocess count, time
to first publication, time to 25%, 50%, 90%, and 100% publication, startup behaviour, and
steady-state execution. Keep cache-disabled compilation, cache installation, and interpreter-only
startup as separate cases.

### Never patch published instructions

Published executable instructions must be immutable. The current linker already obeys this
invariant:

1. copy unpatched compiler or cache bytes into a private mapping;
2. apply relocations and append any range-extension veneer;
3. finalize executable permissions and invalidate the instruction cache; and
4. publish the entry pointers with release ordering.

Cached relocations do not weaken the invariant. A cache record retains unpatched code and
relocation metadata; installation relocates a new unpublished mapping. Relocation is required when
addresses change, but modifying code that another thread can execute is not.

If a call target is unavailable when its caller is ready, the safe choices are to retain the
caller until it can be linked, emit an immutable thunk that reads an atomically updated data slot,
or permanently route that call through a compatible fallback. A data-slot thunk permits more
flexible publication but permanently adds an indirect load and branch. Prefer a direct relocation
when both mappings are known, and do not later rewrite that published callsite merely to remove a
fallback. A single serial installation path is compatible with fully parallel compilation and
makes this ownership rule easier to enforce.

### Keep the optimized interpreter as an independent consumer

The direct frontend's operand stack is compile-time Cranelift SSA bookkeeping. It is not the
runtime `ValueStack` and does not replace interpreter execution. The intended ownership remains:

```text
validated parsed Wasm
    +-- allocated bytecode, R0-R7, fused and synthetic operations --> interpreter
    +-- typed operand/control stacks and semantic values            --> Cranelift
```

The interpreter remains able to run every function, start execution before native code exists, and
serve as fallback. Its register allocation, direct-threaded dispatch, fixed-capacity `ValueStack`,
and synthetic superinstructions need not be removed or made native-friendly.

Attaching type information to bytecode virtual-register uses is feasible and would improve the old
frontend's type selection. It does not by itself recover semantic value identity. One allocated
location can contain distinct definitions at different instruction positions and can be reused
across control-flow edges. Native lowering still needs the reaching definition, exact edge
liveness, genuine merge operands, and the set of values required at a synchronization point.
Representing each location by type and definition generation and solving those facts with dataflow
approaches reconstruction of the typed value graph that direct parsed-Wasm lowering already builds.

The general existence of interpreter state is nevertheless the fundamental OSR cost. Fresh entry
and tier-up must import enough canonical state to continue the activation. The current empty-stack
checkpoint restriction and a separate OSR variant contain that cost at the boundary instead of
making clean native code follow interpreter allocation.

### Attribute the remaining Wasmtime gap by call purpose

The existing structural results support both interpreter-state and helper-call explanations. The
SHA-512 direct body is within one native instruction of Wasmtime, while the allocated-bytecode body
has 149 additional instructions and 107 additional memory operations. This strongly attributes
that workload's old-frontend gap to allocated interpreter locations and their entry/state model.

Direct lowering also substantially improves both d3wasm functions, but still emits 47 calls versus
Wasmtime's 31 in `unzReadCurrentFile()` and 440 versus 284 in `AddActiveInteraction()`. This makes
runtime/helper lowering a plausible part of the remaining gap, but static call count is not dynamic
cost. Classify calls before optimizing them:

- semantically required runtime operations;
- cold trap and error paths;
- avoidable interpreter-bridge helpers;
- memory, table, and reference operations that can be lowered directly;
- calls required only to recover runtime metadata; and
- Cranelift-selected libcalls.

Combine a per-target static call inventory with dynamic inclusive time and execution counts. Do not
inline or duplicate a helper merely because it exists; first show that it executes on the measured
hot path or prevents useful optimization around that path.

### Instruction counting complements sampled profiling

High-frequency Instruments CPU profiling remains statistical PC sampling. A shorter interval
improves visibility into small hot ranges, but does not count every executed instruction. It is
valuable because it observes real M4 execution, wall time, scheduling, frame pacing, and the
microarchitectural effects represented in actual elapsed CPU time.

Callgrind can provide deterministic dynamic instruction counts and simulated branch/cache events
for a suitable Linux build. Time spent running under Valgrind is instrumentation time, not native
execution time, so describe this as instruction-accurate counting rather than instruction-accurate
timing. Its different host architecture and simulated cache model also prevent it from replacing
the Apple Silicon measurements.

Use the measurement methods together:

- static disassembly for code size and instruction shape;
- Callgrind for deterministic dynamic instruction and branch counts;
- hardware counters, where available, for retired instructions, cycles, branches, and misses;
- Instruments with visual-frame markers for actual M4 hot paths and frame correlation; and
- ordinary wall time, phase timing, workload-reported scores, and peak memory for user-visible
  results.

## Success criteria

Correctness is required before performance attribution:

- differential results agree across migrated instruction families;
- existing Rust, focused native-execution, broader LibWasm, and JS Wasm suites pass;
- unsupported functions fall back deterministically; and
- cache and relocation formats distinguish all code flavors.

The first performance comparison should use identical Cranelift versions and compiler settings.
Measure separately:

- optimized CLIF blocks, instructions, values, and block parameters;
- native code size, instruction count, loads, stores, and stack-memory operations;
- fixed native frame size;
- native compilation time and compiler memory;
- execution time or workload-reported score; and
- d3wasm loading and heavy-scene profiles.

Expected improvements are the removal of spurious joins, bank conversions, interpreter-location
live ranges, and synthetic-instruction decoding. Genuine Wasm merge parameters, mutable-local
state, runtime calls, traps, and register-allocation spills remain. Direct lowering should not be
judged by an expectation of zero block parameters or exact Wasmtime parity.
